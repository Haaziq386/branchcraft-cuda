01 / The integration boundary

One page-table idea. Two runtime contracts.

The standalone verifier owns a tree mask and an accepted-path transaction. PyTorch exposes those CUDA operations to a model or experiment. vLLM's ordinary attention backend receives a packed KV tensor and scheduler metadata. Branchcraft implements a specialized one-token decode there; vLLM retains its own cache update and scheduler.

The vLLM backend does not receive a draft tree, so it does not replace vLLM's speculative acceptance algorithm. The shared engineering work is the page-table/KV boundary and a real backend decode path.

03 / The PyTorch contract

The operator has to tell the truth.

A raw pybind call is invisible to much of PyTorch's compilation and alias analysis. Branchcraft registers three dispatcher operators: tree_verify returns a new FP32 tensor; packed_decode_out mutates a preallocated FP16 output; commit_path_ mutates cache K and V. All kernels launch on PyTorch's current CUDA stream.

The transaction's snapshot holds page references. Committing into a shared or snapshotted partial page clones that page before writing accepted nodes. Rollback releases the new page and restores the old mapping and bytes.

04 / What was checked

Evidence at the right level.

Kernel tests, transaction tests, and model-level parity answer different questions. A microbenchmark cannot establish that the vLLM backend is actually used during generation, so the parity script requires an observed custom fast-path marker as well as matching greedy token IDs.

COW
